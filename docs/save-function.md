# ボードのエクスポート・保存・読み込み機能 仕様書

## 1. 概要

### 1.1 目的

ブレインストーミングボードの内容を外部ファイルとして保存し、他のツールで利用したり、後から再読み込みして編集を再開したりできるようにする。

### 1.2 対象機能

本仕様では、以下の3機能を実装対象とする。

1. **このボードをエクスポートする（.svg）**
2. **ボードを保存する（.json）**
3. **ボードを読み込む（.json）**

### 1.3 基本方針

- 既存の共通ボードモデルをデータの基準とする。
- React FlowなどのUI固有のデータ構造を、そのまま保存形式として使用しない。
- 既存のHTTP APIおよびSSEによる同期方式と整合させる。
- 保存・読み込みの際に、編集ロックやリクエストの重複実行防止の仕組みを無視しない。
- 既存のボードモデルやAPIを不必要に変更しない。
- 本機能の実装に必要な変更は、既存仕様との整合性を確認したうえで追加する。

## 2. SVGエクスポート

### 2.1 機能概要

現在表示しているボードをSVG形式のファイルとして出力する。

### 2.2 操作方法

1. ボードのツールバーまたはメニューから「このボードをエクスポートする（.svg）」を選択する。
2. 現在のボード内容をSVG形式に変換する。
3. `.svg` ファイルをユーザーの端末にダウンロードさせる。

### 2.3 出力内容

SVGには、以下の要素を含める。

- カードの背景、形状、色
- カード内のテキスト
- カード間の矢印および接続線
- リアクションなど、ボード上で内容を理解するために必要な表示要素
- カテゴリを識別するための色や表示情報

画面上の操作用ボタン、ツールバー、選択枠、編集用ハンドルなど、ボードの内容そのものではないUI要素は出力しない。

### 2.4 表示とレイアウト

- カードと矢印の相対的な位置関係を維持する。
- カードのサイズと色を可能な限り維持する。
- 日本語を含むテキストが適切に表示されるようにする。
- カードや矢印が出力範囲から欠けないようにする。
- 余白を設け、ボード全体を確認しやすくする。
- SVGを単独のファイルとして開いた場合にも表示できるようにする。

出力範囲は、原則としてボード上の内容全体を含む範囲とする。画面上の表示倍率やスクロール位置に依存して、一部のカードだけが出力される状態を避ける。

### 2.5 編集中のデータの扱い

エクスポート時には、確定済みのボード状態を基準とする。

未確定の編集内容や、許可されていないローカルプレビューを、確定済みの共有データとして出力しない。

編集処理中の場合は、確定済みの状態を出力するか、処理完了までエクスポートを待機させる。どちらを採用するかは既存UIの実装と合わせて決定する。

### 2.6 ファイル名

初期実装では、次の形式を使用する。

`brainstorm-board-YYYYMMDD-HHmmss.svg`

日時は端末のローカル時刻を使用する。

## 3. JSON保存

### 3.1 機能概要

ボードの内容をJSON形式のファイルとして保存する。

JSONは、後からボードを再構築するためのデータ形式とする。SVGとは異なり、見た目だけでなくカードや矢印などの構造を保持する。

### 3.2 操作方法

1. ボードのメニューから「ボードを保存する（.json）」を選択する。
2. 保存対象となるボードの状態を取得する。
3. 所定のJSON形式に変換する。
4. `.json` ファイルをユーザーの端末にダウンロードさせる。

### 3.3 保存対象

以下の情報を保存対象とする。

- カードのIDおよび種類
- カードのテキスト、色、位置、サイズなどの編集可能な属性
- カードのカテゴリに関する情報
- カード間の矢印・接続情報
- リアクションなど、ボードの内容を再構築するために必要な情報
- データ形式のバージョン

実際に保存する属性は、実装時点の共通モデルと矢印・リアクションの正式なデータ構造に合わせる。仕様上まだ決まっていないフィールド名や型を、既存仕様で確定済みのものとして扱わない。

### 3.4 保存対象外

以下は原則として保存しない。

- 編集ロックおよびロックの有効期限
- 編集中のユーザー情報
- 編集中の未確定ドラフト
- SSE接続状態
- クライアントの選択状態や一時的なドラッグプレビュー
- サーバー内部のリクエスト処理履歴
- 一時的な通信エラーや処理中状態

これらは実行時の状態であり、ファイルを読み込んだ際にそのまま復元すべき情報ではない。

共有タイマーは実行時の共有状態として扱い、JSON読み込みによって変更しない。したがって、JSONの保存対象には含めない。

### 3.5 JSON形式

ファイルには、形式の識別と将来的な互換性のため、バージョン情報を含める。

構造の概念例を以下に示す。

```json
{
  "format": "brainstorm-board",
  "version": 1,
  "cards": [],
  "arrows": []
}
```

これは構造を示す例であり、`cards` と `arrows` の内部構造は、実装時点で確定している共通モデルと矢印モデルに従う。

### 3.6 保存時の整合性

- 保存対象は、可能な限り同一時点の確定済みボード状態とする。
- サーバーから取得したスナップショットを使用する場合は、取得したリビジョンを基準に一貫したデータを書き出す。
- JSONの生成に失敗した場合、破損したファイルを正常な保存結果として扱わない。
- 保存操作によって、共有ボードの内容やリビジョンを変更しない。
- 保存操作自体を理由に編集ロックを取得・解放しない。

### 3.7 ファイル名

初期実装では、次の形式を使用する。

`brainstorm-board-YYYYMMDD-HHmmss.json`

## 4. JSON読み込み

### 4.1 機能概要

ユーザーが選択したJSONファイルを読み込み、現在のボード内容をファイル内のデータに置き換える。

読み込みは単なる画面表示の変更ではなく、共有ボードのデータを更新する操作として扱う。

### 4.2 操作方法

1. ボードのメニューから「ボードを読み込む」を選択する。
2. ユーザーが読み込むJSONファイルを選択する。
3. ファイルの形式、バージョン、データ構造を検証する。
4. 読み込み内容の概要を確認できるようにする。
5. ユーザーが置き換えを確認した場合、サーバーに読み込み操作を要求する。
6. サーバーが検証と置き換えを行う。
7. 更新後の確定済みボード状態をクライアントへ反映する。

### 4.3 読み込み前の検証

読み込み前に、少なくとも以下を検証する。

- JSONとして正しく解析できること
- 対応する形式識別子であること
- 対応するバージョンであること
- 必須フィールドが存在すること
- カードや矢印の各フィールドが期待する型であること
- カードIDが重複していないこと
- 矢印の接続先が存在するカードを参照していること
- 座標、サイズ、テキストなどの値が許容範囲内であること
- ファイルサイズや要素数が実装上の上限を超えていないこと

検証に失敗した場合は、ボードを変更せず、読み込みに失敗した理由をユーザーに表示する。

クライアント側の検証だけでなく、サーバー側でも同等の検証を行う。

### 4.4 既存ボードとの置き換え

読み込みは、既存ボードにデータを追加するのではなく、原則としてカードおよび矢印をファイル内の内容に置き換える操作とする。

- 読み込み前に確認ダイアログを表示する。
- 現在のボード内容は、読み込み成功時に置き換える。
- 検証や更新に失敗した場合、現在のボードを維持する。
- 更新はサーバー側で一括して行い、途中まで置き換わった状態を公開しない。
- 置き換え成功後、変更を1回のボード更新として扱い、リビジョンを更新する。
- 変更後の確定済み状態をSSEなど既存の通知方式で共有する。

### 4.5 編集ロックとの整合性

読み込みは、既存の編集ロックの仕組みと整合させる。

原則として、対象ボードに有効な編集ロックが存在する場合は読み込みを拒否する。これにより、他の参加者が編集中の内容を予期せず失うことを防ぐ。

読み込みを実行する場合、サーバーはロックの確認とボードの置き換えを競合しないように処理する。単にクライアントがロックの有無を確認するだけでは不十分とする。

ロックが存在する場合は、ボードを変更せず、再試行できることをユーザーに伝える。

### 4.6 IDと参照関係

読み込むデータのIDは、既存ボードとの衝突や参照関係の破損を防ぐ必要がある。

- カードや矢印のIDを維持するか、新規IDに置き換えるかは、既存モデルと参照構造に合わせて決定する。
- IDを置き換える場合は、矢印の接続先などの参照も同時に更新する。
- 読み込み対象に存在しないカードを参照する矢印は受け入れない。
- 読み込みによって既存の編集ロック情報を復元しない。

### 4.7 タイマーの扱い

読み込み時に、現在の共有タイマーは変更しない。

読み込み前にタイマーが動作していた場合は、その動作状態と残り時間を維持する。読み込み後にタイマーを停止・リセットする処理は行わない。

### 4.8 通信失敗時の扱い

サーバーからの応答が失われた場合、クライアントが読み込みに失敗したと即断して同じ操作を新しいリクエストとして再実行してはならない。

既存仕様の `(clientId, requestId)` による重複実行防止を利用し、同一操作の再試行には同じ `requestId` を使用する。

処理結果が不明な場合は、既存の通信仕様に従って結果を確認または再同期する。成功済みの置き換えを重複して実行しない。

### 4.9 読み込み成功後

- 共有ボードの確定済み状態を更新する。
- 変更されたカードおよび矢印を適切に通知する。
- クライアント側の表示を最新状態に同期する。
- 過去のドラフトやプレビューが新しいボードを上書きしないようにする。
- 必要に応じて、読み込み成功のメッセージを表示する。

## 5. サーバーAPIとの統合

### 5.1 基本方針

既存の `POST /api/boards/:boardId` を利用する方針とする。新たな通信方式や独立したサーバープロセスは導入しない。

ただし、既存のAPIにボード全体の置き換えコマンドが存在しない場合は、読み込み専用のコマンドを追加する必要がある。

コマンド名、リクエスト・レスポンス形式、エラーコードの詳細は、既存の `board-protocol.ts` とサーバー実装に合わせて確定する。

### 5.2 サーバー側の責務

サーバーは、読み込み要求に対して以下を実行する。

1. リクエスト形式を検証する。
2. リクエストの重複実行を確認する。
3. JSON由来のデータを検証する。
4. 対象ボードの編集ロックを確認する。
5. 置き換えを原子的に実行する。
6. ボードのリビジョンを更新する。
7. `onBoardUpdated` など既存の更新処理を、操作単位で適切に実行する。
8. 更新結果をクライアントへ返し、既存の通知方式に従って共有する。

検証または置き換えに失敗した場合、ボードの一部だけが変更されることがないようにする。

### 5.3 自動生成機能との整合性

読み込みを通常のボード更新として扱う場合でも、読み込みによって追加された内容が、意図せず通常の自動追加処理や単語生成処理を連鎖的に起動しないようにする。

読み込み操作を識別できる更新種別を用意し、既存の自動生成処理との関係を明示する。

具体的な生成の開始・停止条件は、既存の生成仕様との整合性を確認して決定する。

### 5.4 リクエストの重複実行防止

読み込み操作も、既存のすべての操作と同じく `(clientId, requestId)` で識別する。

- 同じID・同じ内容の再試行では、置き換えを再実行しない。
- 同じIDで異なる内容が送られた場合は拒否する。
- 重複したリクエストにより、更新処理や通知が重複しないようにする。
- 処理結果の保持と再試行は、既存のリクエスト管理仕様に従う。

## 6. エラー処理

以下のケースでは処理を中止し、現在のボードを維持する。

- ファイルを読み込めない
- JSONの解析に失敗する
- 未対応の形式・バージョンである
- データの検証に失敗する
- カードIDなどに重複がある
- 矢印の参照先が存在しない
- 編集ロックが存在する
- サーバー側で置き換えが拒否される
- 通信エラーにより処理結果を確認できない

エラーメッセージは、ユーザーが次に取るべき行動を理解できる内容にする。通信エラーなどで処理結果が不明な場合は、確定的に「失敗した」と表示しない。

SVGエクスポートやJSON保存でエラーが発生した場合も、共有ボードの状態を変更しない。

## 7. 実装上の責務

| 対象             | 責務                                                         |
| ---------------- | ------------------------------------------------------------ |
| UIコンポーネント | メニュー、ファイル選択、確認、成功・失敗表示                 |
| クライアント処理 | エクスポート用データ取得、JSON解析、事前検証、リクエスト送信 |
| 共通モデル       | カード・矢印などのデータ構造と整合性の基準                   |
| 通信プロトコル   | 読み込みコマンドと応答の定義                                 |
| サーバー処理     | 最終検証、ロック確認、原子的な置き換え、リビジョン更新       |
| 更新通知処理     | 更新結果の共有とクライアントの再同期                         |

SVG生成とJSONのシリアライズ・解析は、可能な限りUIコンポーネントから分離する。

## 8. テスト要件

### 8.1 SVGエクスポート

- 複数のカードと矢印が正しく出力される。
- 日本語や改行を含むテキストが適切に表示される。
- カード全体が出力範囲に収まる。
- 選択枠や操作用UIが出力されない。
- エクスポートによって共有ボードが変更されない。

### 8.2 JSON保存

- 保存したJSONが正しい形式である。
- 必要なカード属性と参照情報が保持される。
- 編集ロックやドラフトなどの一時状態が混入しない。
- 保存後もボードの内容とリビジョンが変化しない。

### 8.3 JSON読み込み

- 正常なJSONを読み込むと、カードと矢印が復元される。
- 不正なJSONや未対応バージョンを拒否する。
- ID重複や無効な参照を拒否する。
- 失敗時に既存ボードが維持される。
- 編集ロックがある場合に置き換えを拒否する。
- 成功時に更新が原子的に反映される。
- 共有タイマーが読み込み前の状態を維持する。
- 複数クライアントが更新後の状態に同期する。
- 同じリクエストの再試行で置き換えが重複実行されない。
- 読み込み後に古いドラフトが新しい内容を上書きしない。

### 8.4 回帰テスト

既存の共通モデル、編集ロック、SSE通知、リビジョン管理、リクエスト重複実行防止、自動生成処理に関するテストが引き続き成功すること。

## 9. 今回の実装範囲

### 実装対象

- SVGエクスポート
- JSON保存
- JSON読み込み
- JSONのバージョン管理と検証
- 読み込み時の確認とエラー表示
- サーバー側の安全なボード置き換え
- 既存のロック・同期・重複実行防止との統合
- 上記機能の単体テストおよび統合テスト

### 今回は対象外

- アカウントや権限システムの新規導入
- 新しいデータベースの導入
- ボードのクラウド保存サービスの追加
- JSONの自動マージ
- 異なるボード間の差分統合
- 過去のすべてのJSONバージョンへの無条件な対応
- SVGを読み込んでボードに復元する機能

## 10. 実装時に確定した事項

- JSON形式は `brainstorm-board`、バージョン1。必須属性は `format`、`version`、`cards`、`arrows`。未知の属性・バージョンは拒否する。
- 共通モデルの通常付箋・関連カード、関連先、リアクション、矢印を保存する。カテゴリ専用のモデル属性は現状ないため追加しない。
- ファイルは最大5 MiB（UTF-8）、カードと矢印はそれぞれ最大10,000個。カードのx/y座標は絶対値1,000,000以下、本文・寸法などは既存モデルの上限を適用する。ブラウザーとサーバーは同じ検証を使い、HTTP本文もストリーム読み込み中に制限する。
- メニューの「JSONで保存」「SVGで出力」「JSONを読み込む」から操作する。ファイル選択後にファイル名・カード枚数・矢印数と共有ボードの置き換え確認を表示する。
- 読み込み要求は既存POST APIの `board.import` コマンドとし、`file` に上記JSONを渡す。サーバーで編集ロックの検査から置き換えまで同期的に実行し、`board-imported` として1回更新・通知する。
- 保存済みファイル内のIDは保持するが、読み込み時には全カードと矢印へ新しいIDを割り当て、関連先・矢印の参照も同時に変換する。読み込み前の遅延要求や下書きが復元データを更新することを防ぐ。
- 全員のロックがなくなるまで読み込みは拒否する。拒否後は改めて読み込める。通信結果が不明な場合は元の要求IDを保持し、再送または再接続後の再確認で結果を回収する。
- 読み込みでは共有タイマーの状態・終了時刻・タイマー予約を維持する。自動生成待機を取り消し、生成途中の古い結果は破棄する。読み込み単独では自動生成を予約せず、以降の通常編集から既存の生成動作に戻る。
- 保存・SVG出力はクライアントが保持する確定済みスナップショットを使う。自分が編集中・送信結果待ち・切断中の場合は操作を無効にする。
- SVGは全カードと矢印の範囲に余白を付け、色・書体・日本語・改行・関連先・リアクションを出力する。ツールバーや編集ハンドルは含めない。長文は全文を残してカード内に収まるよう縮小するため、極端に長い本文は小さく表示される。
- サービスは従来どおり単一プロセス内のメモリを使う。サーバー再起動後のボード保持や、複数サーバー間の共有は今回の変更には含めない。
- 開発時はサービスをグローバル領域へ保持するため、サーバー処理・コマンドを変更した後は開発サーバーを再起動する。再起動前に必要なボードをJSON保存しておく。
- 読み込み未対応の旧サービスが残った場合は `SERVER_RESTART_REQUIRED`（503）で処理開始前に拒否し、再起動手順を表示する。この場合は読み込み待ちを解除してJSON保存を可能にする。結果不明の503や通信失敗では、引き続き元の要求IDを保持する。
- カード0枚、本文が空または空白・改行のみの付箋、概要・関連先・リアクションが空の関連カードは有効なファイルとして扱う。空の付箋でも読み込み先の有効な編集ロックは読み込みを拒否する。ファイル自体が空・空白のみ、`{}`・`null`、必須属性の欠落や不正な参照は受け付けない。

## 11. 完了条件

以下をすべて満たした時点で、本機能の実装完了とする。

- SVG形式でボード全体を出力できる。
- JSON形式でボードの編集可能な内容を保存できる。
- 保存したJSONを読み込み、ボードを復元できる。
- 不正なファイルや競合する編集状態からボードを保護できる。
- 読み込みの成功・失敗が共有ボードの全クライアントに正しく反映される。
- 既存の編集・同期・ロック・生成機能に回帰不具合が発生しない。
- 関連するテストが成功する。
