# カード編集とイベント同期の基礎構造

この文書は、ホワイトボードの図と、それについての議論をまとめた設計メモである。実装済みの仕様を示すものではない。ユーザーが提示した設計と、議論中に挙がった補足・未決事項を区別して記載する。

## 1. 基本方針

ボード上のカードを基本単位として、内容と見た目、配置を管理する。

カードの編集は、サーバーに編集許可を要求してから開始する。サーバーはカード単位で排他ロックを管理し、同じカードに対する編集の競合を防ぐ。編集完了時にサーバーが変更を確定してロックを解除し、そのボードに接続するすべてのクライアントへ編集内容を通知する。

各クライアントはボードの情報を手元に保持し、サーバーからのイベントに応じて情報と表示を更新する。端末とサーバーの同期は、このイベント方式を基本とする。

## 2. 登場する主体

| 主体 | 役割 |
|---|---|
| ユーザー | 端末を操作し、カードを編集する人 |
| クライアント | ユーザーが使用する端末上のアプリ。ボードの情報を保持し、編集UI、編集要求の送信、同期イベントの受信を担当する |
| サーバー | 編集許可、ロックの管理、編集内容の確定、各クライアントへの通知を担当する |

ユーザーとクライアントは別の構造として扱う。「ユーザー側がボードの情報を保持する」とは、具体的にはクライアントがボードの情報を保持することを指す。

## 3. カードのデータ

ユーザーが整理したカードの基本属性は、次の6つである。コード上の属性名が未指定の項目については、説明のための仮称を使用する。

| 属性 | 表記・型の案 | 内容 |
|---|---|---|
| 形状 | `shape` | カードの形を指定する |
| 座標 | `position: { x, y, z }` | `x`、`y` は平面上の位置。`z` は前面・背面の描画優先を表す |
| 色 | `color` | カードの色を指定する |
| 編集中 | `editingUser: optional<User>` | 編集中のユーザーを保持し、編集の重複を防ぐ排他ロックを表す |
| テキスト | `text` | カードに表示する文字列 |
| フォント | `font` | 文字の書体 |

`z` は3次元空間の奥行きではなく、カードの描画順を表す。数値の大小と前後の対応は未決定である。

`editingUser` が未設定なら編集可能、設定済みならそのユーザーが編集中である。サーバーは編集許可時に設定し、編集確定時に未設定へ戻す。取消を設ける場合も、取消時に未設定へ戻す。

初回の写真の読み取りでは回転 `rotation` や追加設定 `optional / params` も候補として挙がったが、その後ユーザーが示した上記の6属性には含まれていない。特に「編集中」の型はユーザーの説明により `optional<User>` と整理されたため、汎用の追加設定としては扱わない。回転も現時点の基本属性には含めず、必要性が生じた際に検討する。

## 4. 編集リクエストの情報の流れ

ホワイトボード右上の図は、左からユーザー、クライアント、サーバーの3本の線を持つシーケンス図である。縦方向は時間の経過、横方向の矢印は主体間の情報の受け渡しを表す。

1. ユーザーが端末を操作し、カードの編集を開始しようとする。
2. クライアントがサーバーに、カード1つ分の編集許可を要求する。
3. サーバーが編集許可を返す。
4. 許可を受け取ったクライアントが、UI上で編集を可能にする。
5. ユーザーが編集を終え、その完了をクライアントに伝える。
6. クライアントが編集内容をサーバーに送る。
7. サーバーが編集内容を確定し、カードのロックを解除する。
8. サーバーが、そのボードに接続するすべてのクライアントに編集内容を通知する。編集を行ったクライアントも通知対象に含む。
9. 各クライアントが、保持しているボード情報と表示を更新する。

サーバーでは、編集許可の判断時に対象カードのロックを確認する必要がある。すでに他の編集が進行している場合の拒否応答やUIは、具体的な仕様を今後決める。

## 5. クライアントが保持する状態

クライアントは、表示対象のボードと、そのボードに含まれるカードの情報を保持する。サーバーから確定した変更が届いたら、対応する情報を更新する。

議論中の補足として、次の2つを区別する案が挙がった。

- **共有済みのボード情報**：サーバーが確定し、クライアントが同期によって受け取った状態。
- **編集中の仮の内容**：編集を許可されたクライアントが、編集完了まで手元に保持する変更。

提示された流れでは、編集内容は完了時にまとめてサーバーへ送られる。編集中の入力を逐次ほかのクライアントへ配信する方式は、現時点では含めていない。

## 6. 必要な構造の整理

以下は議論から整理した構造の案であり、識別子などの具体的な型は未決定である。

| 構造 | 保持する情報の案 |
|---|---|
| ユーザー | `userId` など、操作する人を識別する情報 |
| クライアント | `clientId`、利用中の `userId`、接続先の `boardId` など |
| ボード | `boardId`、カード一覧、同期用の更新番号など |
| カード | `cardId` と、前述の6つの基本属性 |
| ロック管理情報 | 編集対象カード、編集中のユーザー、許可先のクライアントなど |
| 同期イベント | 編集許可や編集確定など、サーバーとクライアントの間で伝える情報 |

`cardId` は、編集要求や変更通知で対象カードを一意に指定するために必要になる。

### ユーザーとクライアントの区別

同じユーザーが複数の端末から接続する可能性がある。カードの `optional<User>` だけでは、どの端末に編集を許可したかを区別できない。

そのため、カードにはユーザーが指定した `editingUser: optional<User>` を持たせ、サーバーでは別途、許可先のクライアントを特定するロック管理情報を保持する案が挙がった。ロック管理情報の保存形式や、カードの属性との整合性を保つ方法は未決定である。

## 7. イベントの整理案

具体的なイベント名、通信方式、データ形式は未決定である。必要になる情報の受け渡しは、概念的には次のように整理できる。

| 方向 | 情報の受け渡し | 内容 |
|---|---|---|
| クライアント → サーバー | 編集許可要求 | 対象カードの編集権を要求する |
| サーバー → 要求元クライアント | 編集許可応答 | 対象カードの編集を許可する。拒否時の応答は今後定義する |
| クライアント → サーバー | 編集完了要求 | 対象カードの編集内容を送り、確定を求める |
| サーバー → ボード内の全クライアント | 編集確定通知 | 確定した編集内容を伝え、各クライアントのボード情報を更新する |

ロックの取得・解除をほかのクライアントにも通知するか、確定通知にロック解除後の状態をどう含めるかは、今後決める。

## 8. 実装時に検討する補足事項

以下は議論中に提案した、基本方式を成立させるための検討事項である。具体的な方式や値はまだ確定していない。

- **初回取得**：接続時にボード全体の情報を取得する。
- **再接続時の同期**：切断中にイベントを取り逃した場合も、サーバーと状態を合わせる。
- **更新番号**：イベントの重複、欠落、順序のずれを判別できるようにする。ボード単位・カード単位のどちらで持つかは未決定。
- **ロックの有効期限**：編集中に端末が切断されても、ロックが残り続けないようにする。期限や延長方式は未決定。
- **編集取消**：編集を中断し、変更を確定せずにロックを解除する流れを設ける。
- **編集権の確認**：サーバーは編集内容を受け取った際、送信元が現在の編集権を持つクライアントかを確認する。
- **確定処理の整合性**：変更の確定とロック解除を一体の処理として扱い、その結果を各クライアントに通知する。

カード同士の親子関係、接続関係、グループについては、最初の図から可能性が挙がったものの、必要性や仕様は確認されていないため、今回の基本構造には含めない。

# 開発方針

両方を開発するときは、**「どこで動くコードか」と「何を共通化するか」を分けて考える**と分かりやすいです。クライアントとサーバーを同じ言語・同じリポジトリで開発することもできます。

今回なら、すでに使っている **TypeScript＋Next.jsで、画面とHTTP APIの両方を作れます**。

**1. クライアントとサーバーは、別々の場所で動く**

今回のボードでは、役割をこう分けます。

| 区分 | 動く場所 | 担当 |
|---|---|---|
| クライアント | 各ユーザーのブラウザ | ボードの表示、ドラッグ、文字入力、編集中の下書き |
| サーバー | サーバー側の実行環境 | 編集許可、変更の確定、保存、ほかの端末への通知 |
| 共通コード | 両方から読み込む | `Board`・`Card` の型、データの更新処理 |

ここで大事なのは、**コードを共有しても、メモリ上のデータは共有されない**ことです。

同じ `Board` 型を使っていても、ブラウザA・ブラウザB・サーバーは、それぞれ別のボード情報を持ちます。その内容を合わせるために通信が必要です。

**2. Next.jsは、画面とサーバーの入口を一緒に作れる**

Reactは画面を作るライブラリで、Next.jsはそれにサーバー側の機能などを加えたフレームワークです。サーバー側でもTypeScriptで書けます。

例えば、今のプロジェクトを次のように整理できます。これは今後の構成例です。

```text
src/
  domain/
    board.ts                 ← 両方で使う型・更新処理

  components/
    BoardEditor.tsx          ← ボードの表示・操作

  app/
    page.tsx                 ← ページ
    api/
      boards/
        [boardId]/
          route.ts           ← HTTPリクエストの受付

  server/
    board-service.ts         ← 編集許可・変更確定
    board-repository.ts      ← 保存・読み込み
```

Next.jsでは、`route.ts` に `GET` や `POST` の処理を書くと、HTTP APIを作れます。ブラウザは `fetch()` でそのAPIにアクセスします。

なお、`server` というフォルダー名だけで実行場所が保証されるわけではありません。サーバー専用コードをクライアントに読み込ませない境界も必要です。

**3. 通信には「要求への応答」と「変更の通知」がある**

今回のアプリでは、この2種類を考えます。

| 通信方式 | 特徴 | ボードでの用途例 |
|---|---|---|
| HTTP API | クライアントが要求し、サーバーが返答する | 初回取得、編集許可要求、編集内容の送信 |
| WebSocket | 接続を維持して双方向に送れる | 編集状態や確定した変更の即時通知 |
| SSE | 接続を維持してサーバーから通知できる | HTTPで編集要求を送り、結果の通知を受信 |

**イベントで同期する設計だからといって、必ずWebSocketを使うわけではありません。** 今回の「編集完了時にまとめて通知する」方式なら、HTTP＋SSEも候補になります。

WebSocketを選ぶ場合は配置先も関係します。Next.jsのHTTP APIが短時間で終了する関数として動く環境では、WebSocketの接続を維持できないため、常時稼働するサーバーや外部の配信サービスを組み合わせます。

**4. 共通化するのは、型と環境に依存しない処理**

例えば、同じ更新関数をそれぞれの場所で使えます。

```ts
// サーバー：編集権を確認してから、確定した変更を反映
const nextBoard = replaceCard(serverBoard, confirmedCard);

// クライアント：サーバーから届いた確定内容を反映
setBoard(current => replaceCard(current, receivedCard));
```

サーバーにある関数をクライアントから直接実行しているのではなく、**同じ関数のコードを、それぞれの環境で実行しています**。

また、TypeScriptの型は開発時のチェックです。通信で届いたデータが正しいか、送信者に編集権があるかは、サーバーで別途確認します。

今回の開発順序としては、**共通モデル → ブラウザ内で動く編集画面 → HTTP APIと保存 → 複数端末への通知**と進めると、段階ごとに動作を確認できます。先ほど作った `board.ts` は、この最初の共通モデルに当たります。
