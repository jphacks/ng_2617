# カード編集とイベント同期の基礎構造

この文書は、ホワイトボードの図と、それについての議論をまとめた設計メモである。ユーザーが提示した設計と、議論中に挙がった補足・未決事項を区別して記載する。2026年10月25日に統合実装を行った。現在の契約は [implementation.md](./implementation.md)、[board-server.md](./board-server.md)、[board-client.md](./board-client.md) を参照する。
初期の図を基に、2026年10月25日までの合意を反映する。共通モデルと操作の詳細は [frontend-merge-plan.md](./frontend-merge-plan.md)、期限・問い合わせ・自動追加は [edit-lifecycle-plan.md](./edit-lifecycle-plan.md) を参照する。現在の実装の契約は [board-client.md](./board-client.md)・[board-server.md](./board-server.md) に分ける。

## 1. 基本方針

ボード上のカードを基本単位として、内容と見た目、配置を管理する。

カードの本文・見た目・位置の保存にはサーバーの編集許可を必要とする。サーバーはカード単位の排他ロックを管理し、複数選択の移動では対象全体の取得・確定・解除を一括で行う。
ドラッグは許可待ちから本人の画面だけで仮移動させ、拒否されたら最新の確定位置に戻す。既に編集中と分かるカードは移動を開始させない。
リアクション・矢印・削除は専用要求による即時操作とする。削除対象カードが編集中なら全体を拒否する。
編集完了や即時操作の反映後は、そのボードに接続するすべてのクライアントへ確定状態を通知する。

各クライアントはボードの情報を手元に保持し、サーバーからのイベントに応じて情報と表示を更新する。端末とサーバーの同期は、このイベント方式を基本とする。

## 2. 登場する主体

| 主体 | 役割 |
|---|---|
| ユーザー | 端末を操作し、カードを編集する人 |
| クライアント | ユーザーが使用する端末上のアプリ。ボードの情報を保持し、編集UI、編集要求の送信、同期イベントの受信を担当する |
| サーバー | 編集許可、ロックの管理、編集内容の確定、各クライアントへの通知を担当する |

ユーザーとクライアントは別の構造として扱う。「ユーザー側がボードの情報を保持する」とは、具体的にはクライアントがボードの情報を保持することを指す。

## 3. カードのデータ

ユーザーが整理したカードの基本属性は、次の6つである。コード上の属性名が未指定の項目については、説明のための仮称を使用する。

| 属性 | 表記・型の案 | 内容 |
|---|---|---|
| 形状・大きさ | `shape` | 統合計画では `{ width, height }` とする |
| 座標 | `position: { x, y, z }` | `x`、`y` は平面上の位置。`z` は前面・背面の描画優先を表す |
| 色 | `color` | カードの色を指定する |
| 編集中 | `editingUser: optional<User>` | 編集中のユーザーを保持し、編集の重複を防ぐ排他ロックを表す |
| テキスト | `text` | カードに表示する文字列 |
| フォント | `font` | 文字の書体 |

`z` は3次元空間の奥行きではなく、カードの描画順を表す。数値の大小と前後の対応は未決定である。
現在の共通モデルはこの6属性を基にしている。統合計画ではWordCard・BlockCard、構造化ID、リアクション定義、Anchorを持つ矢印を追加する。具体的な型はmerge planを参照する。

`editingUser` が未設定なら編集可能、設定済みならそのユーザーが編集中である。サーバーは編集許可時に設定し、編集確定時に未設定へ戻す。取消を設ける場合も、取消時に未設定へ戻す。

初回の写真の読み取りでは回転 `rotation` や追加設定 `optional / params` も候補として挙がったが、その後ユーザーが示した上記の6属性には含まれていない。特に「編集中」の型はユーザーの説明により `optional<User>` と整理されたため、汎用の追加設定としては扱わない。回転も現時点の基本属性には含めず、必要性が生じた際に検討する。

## 4. 編集リクエストの情報の流れ

ホワイトボード右上の図は、左からユーザー、クライアント、サーバーの3本の線を持つシーケンス図である。縦方向は時間の経過、横方向の矢印は主体間の情報の受け渡しを表す。

1. ユーザーが端末を操作し、カードの編集を開始しようとする。
2. クライアントが対象カードの編集許可を要求する。複数移動では対象一覧を送る。
3. ドラッグでは、応答待ちの間も本人の画面で仮移動する。サーバーは対象全体のロックを確認して許可または拒否する。
4. 許可されたら保存可能な編集として継続する。拒否されたら仮移動を取り消して最新の確定位置へ戻す。
5. ユーザーが編集を終え、その完了をクライアントに伝える。
6. クライアントが編集内容をサーバーに送る。
7. サーバーが対象全体の編集内容を確定し、ロックを解除する。`onLockReleased` で後始末し、影響ID一覧を `onBoardUpdated` へ1回渡す。
8. サーバーが、そのボードに接続するすべてのクライアントに確定状態をSSEで通知する。編集を行ったクライアントも通知対象に含む。
9. 各クライアントが、保持しているボード情報と表示を更新する。

操作要求はHTTPで送る。サーバーでは編集許可・内容・ロックを検証し、一括操作は全成功または全拒否とする。単一・複数とも1回の貸し出しに1つのlockIdを使う。具体的なコマンド名・型は後続で決める。
リアクション・矢印・削除は、内容が確定した専用要求から直接検証・反映へ進み、カードロックを一時的に作らず `onBoardUpdated` へ合流する。

## 5. クライアントが保持する状態

クライアントは、表示対象のボードと、そのボードに含まれるカードの情報を保持する。サーバーから確定した変更が届いたら、対応する情報を更新する。

次の状態を区別する。

- **共有済みのボード情報**：サーバーが確定し、クライアントが同期によって受け取った状態。
- **許可待ちの仮表示**：ドラッグの即応性のため本人の画面で保持する位置。サーバーに保存済みという意味ではない。
- **許可済みの下書き**：編集完了まで手元に保持する変更。確定／取消要求済みの状態も区別し、通信タイムアウトだけでは回収に必要な情報を消さない。
- **画面固有の状態**：選択・表示範囲・生成カードへの案内。共有Boardには保存しない。

通常の確定は編集完了時にまとめて送る。期限確認で未反映の変更があれば途中保存する。ポインター移動のたびに座標を確定・配信する方式は含めない。

## 6. 必要な構造の整理

以下は構造の整理であり、共通型の詳細はmerge planへ集約する。

| 構造 | 保持する情報の案 |
|---|---|
| ユーザー | `userId` など、操作する人を識別する情報 |
| クライアント | `clientId`、利用中の `userId`、接続先の `boardId` など |
| ボード | `boardId`、カード一覧、独立した矢印一覧、用途を限定しない共有タイマー。同期用のrevisionはイベント側で保持する |
| カード | `CardId`、共通属性、WordCard・BlockCardの種別と専用項目 |
| ロック管理情報 | 1回の貸し出しを識別するlockId、対象cardIds、ユーザー・端末・期限・問い合わせとの対応。カードIDからの索引も持つ |
| 同期イベント | 編集許可や編集確定など、サーバーとクライアントの間で伝える情報 |

`cardId` は、編集要求や変更通知で対象カードを一意に指定するために必要になる。

### ユーザーとクライアントの区別

同じユーザーが複数の端末から接続する可能性がある。カードの `optional<User>` だけでは、どの端末に編集を許可したかを区別できない。

そのため、カードには表示用の `editingUser: optional<User>` を持たせ、サーバーでは別途、許可先のユーザー・端末・lockIdを照合する。lockIdは台帳の識別番号であり、カード本体には保存しない。単一・複数の期限・問い合わせ・確定・取消を貸し出し単位で揃える。具体的な型名や永続保存の形式は未確定である。

## 7. イベントの整理案

操作要求はHTTP、更新・生成結果はSSEで通知する方針とする。新しいイベント名・詳細な形式はmerge planで案と未確定事項を分ける。

| 方向 | 情報の受け渡し | 内容 |
|---|---|---|
| クライアント → サーバー | 編集許可要求 | 対象カードの編集権を要求する |
| サーバー → 要求元クライアント | 編集許可応答 | 対象カードの編集を許可する。拒否時の応答は今後定義する |
| クライアント → サーバー | 編集完了要求 | 対象カードの編集内容を送り、確定を求める |
| サーバー → ボード内の全クライアント | 編集確定通知 | 確定した編集内容を伝え、各クライアントのボード情報を更新する |
| クライアント → サーバー | 即時操作要求 | リアクション・矢印・削除を、本文の下書きとは独立して確定する |
| サーバー → ロック所有端末 | 編集状態の問い合わせ | 期限到達時に編集中か確定／取消要求済みかを確認する |
| クライアント → サーバー | 問い合わせへの返答 | 状態・必要な最終内容・対象ロックと問い合わせとの対応を返す |
| サーバー → ボード内の全クライアント | 生成完了通知 | 追加確定後のボード・revision・生成カードID一覧を届ける |

ロックの取得・解除を含め、各更新の完了後の全体スナップショットを配信する。取得・更新・解除の途中状態を配信しない。

### 終了処理と自動追加の接続

通常要求と問い合わせ経由の確定・取消は同じ処理を使い、保存または取消 → ロック解除 → `onLockReleased` → `onBoardUpdated` → 配信へ進む。
途中保存して継続する場合は解除処理を通さず、期限を再設定する。先に終了したロックへの遅い返答は無視する。
`onBoardUpdated` は操作全体の影響ID一覧と更新種別を受け取り、全体revisionと配信を更新する。カード系更新では編集の最終更新情報を記録し、待機をリセットしてロック0件なら開始する。共有タイマーの操作では、この編集情報・待機・生成の有効性を変えない。
待機満了時は、生成に使える本文あり・最後のカード系更新が自動生成以外・ロック0件・生成中でないことをANDで判定する。空カードや空白・改行だけの本文は生成入力としない。
新規作成は空カードをロックなしで共有し、本文欄へのフォーカスで別途編集許可を要求する。空白キャンバスへのタップかCtrl／⌘＋Enterで確定、Enter改行、Escape取消を基本動作とし、キー設定変更は追加機能に分ける。フォーカス移動だけでは確定せず、タップをパン・ドラッグと区別する。
関連先選択では参照元の貸し出しを維持し、参照先カードを編集開始しない。Escapeは選択だけを中止し、空白タップで参照元の下書きを確定する。
Delete／Backspaceは入力欄なら文字削除、キャンバス上の選択対象ならゴミ箱と同じ削除要求へ接続する。カード全体のリサイズは移動と同じ経路でサイズ・必要な位置を確定し、本文欄だけの縦リサイズを置き換える。
Reactionはアプリ共通の固定一覧、サンプル復元はロック0件を条件としたカード・矢印の一括置換とし、共有タイマーは保持する。UIはAdjustのpage.tsxを基準にする。
リアクションはユーザー・種類ごとに1件で、自分の付与だけを取消可能とする。矢印は自己接続・同一接続の重複を禁止し、異なるAnchor・逆向き・循環を許可する。通信は明示した追加・取消・作成・削除で行い、変更なしなら更新しない。
共有タイマーは初期5分停止のカウントダウンで、0秒で停止する。サーバーで0秒への遷移を確定したときに空のonTimerFinishedを1回呼び、停止・リセットでは呼ばない。
手動・時限式のAI生成は同じ関数に関連性を渡す。手動はUI選択値、時限式は中固定とする。
生成中・完了・失敗・競合破棄はgenerationIdで対応付けて全端末へ通知し、途中参加・再接続でも現在状態を取得する。開始・失敗・破棄の通知だけではBoardの更新後処理を呼ばず、カード追加の確定時に呼ぶ。
同じclientId・requestIdの同内容再送は結果を再利用し、異内容なら拒否してサーバーに識別情報を含むエラーログを出す。更新やフックを二重実行せず、クライアントから別途エラーを送るAPIも設けない。

## 8. 実装時に検討する補足事項

以下は議論中に提案した、基本方式を成立させるための検討事項である。具体的な方式や値はまだ確定していない。

- **初回取得**：接続時にボード全体の情報を取得する。
- **再接続時の同期**：切断中にイベントを取り逃した場合も、サーバーと状態を合わせる。
- **更新番号**：ボード単位のrevisionと個別要求の完了判定を分ける。SSE接続境界と、生成通知のeventIdによる重複判定を設計する。
- **ロックの有効期限**：貸し出し単位の期限到達時に問い合わせ、継続・終了・無応答解除を扱う。具体的な期限や台帳の型名は未確定。
- **編集取消**：編集を中断し、変更を確定せずにロックを解除する流れを設ける。
- **編集権の確認**：サーバーは編集内容を受け取った際、送信元が現在の編集権を持つクライアントかを確認する。
- **確定処理の整合性**：変更の確定とロック解除を一体の処理として扱い、その結果を各クライアントに通知する。

カード同士の関係はBlockCardからの参照と独立した矢印で扱い、所有・親子関係にはしない。複数選択は一括操作の対象集合として扱い、永続的なグループオブジェクトの追加を意味しない。

# 開発方針

両方を開発するときは、**「どこで動くコードか」と「何を共通化するか」を分けて考える**と分かりやすいです。クライアントとサーバーを同じ言語・同じリポジトリで開発することもできます。

今回なら、すでに使っている **TypeScript＋Next.jsで、画面とHTTP APIの両方を作れます**。

**1. クライアントとサーバーは、別々の場所で動く**

今回のボードでは、役割をこう分けます。

| 区分 | 動く場所 | 担当 |
|---|---|---|
| クライアント | 各ユーザーのブラウザ | ボードの表示、ドラッグ、文字入力、編集中の下書き |
| サーバー | サーバー側の実行環境 | 編集許可、変更の確定、保存、ほかの端末への通知 |
| 共通コード | 両方から読み込む | `Board`・`Card` の型、データの更新処理 |

ここで大事なのは、**コードを共有しても、メモリ上のデータは共有されない**ことです。

同じ `Board` 型を使っていても、ブラウザA・ブラウザB・サーバーは、それぞれ別のボード情報を持ちます。その内容を合わせるために通信が必要です。

**2. Next.jsは、画面とサーバーの入口を一緒に作れる**

Reactは画面を作るライブラリで、Next.jsはそれにサーバー側の機能などを加えたフレームワークです。サーバー側でもTypeScriptで書けます。

例えば、今のプロジェクトを次のように整理できます。これは今後の構成例です。

```text
src/
  domain/
    board.ts                 ← 両方で使う型・更新処理

  components/
    BoardEditor.tsx          ← ボードの表示・操作

  app/
    page.tsx                 ← ページ
    api/
      boards/
        [boardId]/
          route.ts           ← HTTPリクエストの受付

  server/
    board-service.ts         ← 編集許可・変更確定
    board-repository.ts      ← 保存・読み込み
```

Next.jsでは、`route.ts` に `GET` や `POST` の処理を書くと、HTTP APIを作れます。ブラウザは `fetch()` でそのAPIにアクセスします。

なお、`server` というフォルダー名だけで実行場所が保証されるわけではありません。サーバー専用コードをクライアントに読み込ませない境界も必要です。

**3. 通信には「要求への応答」と「変更の通知」がある**

今回のアプリでは、この2種類を考えます。

| 通信方式 | 特徴 | ボードでの用途例 |
|---|---|---|
| HTTP API | クライアントが要求し、サーバーが返答する | 初回取得、編集許可要求、編集内容の送信 |
| WebSocket | 接続を維持して双方向に送れる | 編集状態や確定した変更の即時通知 |
| SSE | 接続を維持してサーバーから通知できる | HTTPで編集要求を送り、結果の通知を受信 |

操作要求はHTTP、更新・生成状態・生成結果はSSEで通知します。全端末への配信とSSEの初期スナップショットによる初期取得まで実装済みです。

WebSocketを選ぶ場合は配置先も関係します。Next.jsのHTTP APIが短時間で終了する関数として動く環境では、WebSocketの接続を維持できないため、常時稼働するサーバーや外部の配信サービスを組み合わせます。

**4. 共通化するのは、型と環境に依存しない処理**

例えば、同じ更新関数をそれぞれの場所で使えます。

```ts
// サーバー：編集権を確認してから、確定した変更を反映
const nextBoard = replaceCard(serverBoard, confirmedCard);

// クライアント：サーバーから届いた確定内容を反映
setBoard(current => replaceCard(current, receivedCard));
```

サーバーにある関数をクライアントから直接実行しているのではなく、**同じ関数のコードを、それぞれの環境で実行しています**。

また、TypeScriptの型は開発時のチェックです。通信で届いたデータが正しいか、送信者に編集権があるかは、サーバーで別途確認します。

今回の開発順序としては、**共通モデル → ブラウザ内で動く編集画面 → HTTP APIと保存 → 複数端末への通知**と進めると、段階ごとに動作を確認できます。先ほど作った `board.ts` は、この最初の共通モデルに当たります。
