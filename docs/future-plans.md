# 継続利用に向けた今後の設計方針

本書では、共同編集型ブレーンストーミングボード「芽生え」の継続利用に向けた拡張方針を示す。データの永続化、同期処理の最適化、ユーザー・ルーム管理、アクセス制御・プライバシーの4領域を対象とする。
2026年10月26日時点の実装を前提とし、以下の拡張は今後の開発に向けた検討事項とする。データベースや認証方式、実装順序・時期は未決定である。

## 現状と目指す方向

| 領域 | 現在のMVP | 今後の方向性 |
| --- | --- | --- |
| データの永続化・自動保存 | 単一サーバープロセスのメモリで管理。ボードのカードや関連情報はJSONで手動保存・復元できる | サーバー側で自動保存し、再起動後も作業を継続できるようにする |
| リアルタイム同期・性能 | SSEとHTTP応答にボード全体を含める。全体の複製・配信による負荷が懸念される | 差分配信・再接続時の回収を検討し、通信量・CPU負荷・メモリ使用量を抑える。負荷試験で効果を確認する |
| ユーザー・ルーム管理 | 本人確認を伴わない識別子を使用。ルームID・URLを共有して参加する | アカウント、ユーザー情報・参加ルームの継続管理、ルーム所有者・参加者・招待の仕組みを整える |
| アクセス制御・プライバシー | 認証・アクセス制御は未導入で、非公開ルームの保証はない | 公開・非公開設定と閲覧・編集権限を設け、誰と共有するかを選べるようにする |

## 詳細設計に向けた論点

### データの永続化・自動保存

ボードの保存と、編集ロック・接続情報などの一時状態を分けて考える。タイマーや進行中のゲームを再起動後にどう扱うかも含め、保存対象と復旧方法を検討する。
既存のJSON保存・復元は活かしながら、自動保存のタイミングと失敗時の扱い、要求の二重実行防止を再起動後にどこまで保証するかを詳細設計で決める。

### リアルタイム同期・性能

更新処理では `revision` と変更対象の `objectIds` を扱っているが、配信内容は全体スナップショットで、再接続用の更新履歴は保持していない。
`objectIds` は更新フックに渡す影響対象の一覧であり、それ自体が過去の状態や差分データを保存する仕組みではない。

#### 差分同期の機能案

通信量と配信負荷の削減に向けて、次の機能を検討する。

| 機能案 | 想定する動作 |
| --- | --- |
| 初回全体取得・以後の差分配信 | 初回接続では全体スナップショットと `revision` を取得し、その後の通常更新は差分イベントで共有する |
| カード・矢印の追加・更新・削除の同期 | 変更後のカード・矢印と削除されたIDを送り、受信側の状態へ反映する |
| 更新番号を検証して差分を適用 | 差分の `baseRevision` がクライアントの保持する `revision` と一致することを確認し、適用後に新しい `revision` へ進める |
| 欠落・不整合からの全体再同期 | 更新の欠落を検出した場合は差分の適用を止め、全体スナップショットから整合した状態を復元する |
| 共有状態の差分同期 | タイマー・ボード設定・神経衰弱の進行や入力も対象にする。`objectIds` が空の更新も表現できるようにする |
| 全体配信への切り替え | JSON読み込みなど、ボード全体を置き換える更新では、全体スナップショットを送る方式も選べるようにする |
| HTTP応答の軽量化 | SSEに加えて操作要求への応答も見直し、成功・拒否の結果や編集権の情報を保ちながら、全体データの転送を減らす |

例えば、全体取得（revision 20）の後に、カード更新（20→21）、カード追加（21→22）、矢印削除（22→23）の差分を順に反映する。クライアントがrevision 19の状態で20→21の差分を受信した場合は、全体スナップショットから再同期する。

#### 差分生成の設計方針

更新処理が把握する影響対象から、変更後のオブジェクトと削除されたIDを取り出す方式を検討する。過去の全体スナップショットの蓄積や、更新ごとの全体比較に伴うメモリ使用量・CPU負荷の抑制を目指す。
カード削除に伴う関連先の除去・接続矢印の削除など、間接的な変更も同じ更新に含める。現行の削除処理もこれらを影響対象に集めているため、その範囲を差分生成でも維持する。

差分イベント `BoardPatch` の形式案では、`baseRevision`・`revision` に加えて、`upsertCards`・`removedCardIds`・`upsertArrows`・`removedArrowIds` を持たせる。変更されたカード・矢印をオブジェクト単位で追加・置換する方式を想定し、位置などの属性だけを送る方式は追加の検討事項とする。
共有状態の変更・解除の表現や、ボードIDなどの識別情報も含め、イベント型の詳細は今後設計する。

#### 追加の設計検討事項

差分同期の整合性、復旧方法、配信単位について、以下を検討する。

- **初期取得・再同期と購読の境界：** 現行のSSEで初期状態を受け取る仕組みを踏まえ、全体取得と差分の購読の間に更新の欠落が生じないようにする。
- **重複・遅延した応答の扱い：** HTTPとSSEで同じ更新が届いても二重適用せず、古い状態で最新状態を巻き戻さない。状態の適用とは別に、`requestId` に対応する成功・拒否や編集権の結果は回収する。
- **ボード本体以外の通知：** `revision` とは別に進む `generationSequence`、生成カードの案内、対象端末に限定した編集権・期限確認の通知も維持する。差分を共有する際に、他の参加者へロックIDなどを配信しない。
- **神経衰弱の入力単位での同期：** 入力更新のたびにゲーム状態全体を送る負荷も考慮し、進行状態と参加者ごとの下書きを分けて更新する案を比較する。
- **再接続時の差分回収：** 全体スナップショットによる復帰を基本案として検討する。将来的には件数・期間を制限した差分履歴を保持し、不足分だけを再配信する方式も検討する。履歴の範囲外では全体取得へ戻す。保存範囲と再起動時の扱いは未決定である。

#### 性能評価

整合性を維持しながら転送量を削減することを目標とする。神経衰弱の連続入力などを含め、カード数・参加人数・更新頻度を変えて通信量・CPU負荷・メモリ使用量を計測する。削減効果や処理可能な規模は、計測結果に基づいて判断する。

実装の参照先：[更新・配信処理](../src/server/board-service.ts)・[イベント型](../src/domain/board-protocol.ts)・[受信状態の反映](../src/client/board-client.ts)・[HTTP/SSE通信](../src/client/http-board-transport.ts)。

### ユーザー・ルーム管理

現在の `userId` はブラウザの `localStorage` に保存する自己申告の識別子で、`clientId` は画面のマウントごとに発行する接続の識別子。編集ロックは同時操作の競合を防ぐ仕組みであり、認証された利用者に限定する機能ではない。
今後は、アカウントとの対応付け、既存のボード・リアクションの扱い、ルームの所有者・参加者管理、招待方法を検討する。

### アクセス制御・プライバシー

公開・非公開ルームと閲覧・編集権限を検討し、画面の操作制限に加えてHTTP API・SSE接続でも権限を検証する方針を整理する。招待の失効や参加者の権限変更を既存の接続にどう反映するかも詳細設計の対象とする。
現在は候補語の生成時にカード本文をGeminiへ送信しているため、非公開ルームの設計では外部AIへの送信範囲・利用者への説明・利用設定も併せて検討する。
