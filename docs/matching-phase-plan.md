# 神経衰弱フェーズの初期検討記録

確認日：2026年10月25日。本書は実装前の設計整理。確認済みのゲームルール、現行コードから確認した事実、追加する設計案、残る確認事項を分けて記載する。機能のコード変更は行っていない。

> **最新仕様は[ゲームUI設計](./matching-game-ui.md)を参照する。以下の本文は初期検討の記録であり、現行の決定事項として実装しない。** その後の合意では、作者情報を残さず全カードのゲーム用コピーを作り、通常ボードとゲーム専用UIを切り替える。元カードの表示・非表示の属性や復元処理は追加しない。選択・入力各10秒は既存のタイマーを活用し、約10枚の表示枠へ未使用単語をランダムに取得・補充する。時間切れで戻したカードの表示枠は変えない。入力画面は左右配置で、選び直しはなし。1人でも開始・継続でき、誰かが編集中なら開始できない。中断確認は共有し、誰か1人の確定で終了する。アイデアは既存の単語追加と同様の経路で配置し、IME変換中の期限到達ではその時点の入力を確定する。途中保存・再開は設けない。以下にある開始人数・独立タイマー・作者対応・全カードの表示などの旧案は、この更新で置き換えられている。

## 1. 目的・確認済みのルール・現在の実装

今回の「神経衰弱」は、**手番のユーザーが単語カードを2枚指定し、その組み合わせから全員がそれぞれアイデアを書く機能**を指す。

**誰でも開始ボタンを押して手動で開始し、未使用の単語カードが2枚未満になったら終了する。** 最初の担当は開始ボタンを押したユーザー。単語出しの共有タイマーが0秒になっても自動開始しない。

対象は開始時点で本文のある単語カード（`WordCard`）。裏向きにし、シャッフルした配置で表示する。神経衰弱が終了したら元の配置・表向き表示へ戻し、生成したアイデアを残して通常の編集できるボードへ戻る。

1. 全員で1つの盤面を共有する。現在の手番ユーザーが盤面上の2枚を指定する。
2. 指定した2枚を関連先に持つ `BlockCard` を、手番ユーザーを含む全員へ1枚ずつ配る。
3. 2枚目の指定と全員分の入力用カードの作成を確定した時点から、全員共通で **10秒**を計測する。10秒は前の確認内容を引き継ぐ。
4. 各ユーザーが自分のカードに書き込む。**入力途中から全員の本文を見られる。** 盤面への追加は入力時間の終了時に行う。
5. 10秒後、本文のあるカードだけを盤面へ追加する。途中までの入力も残し、空のカードは追加しない。追加したカードと書いたユーザーを関連付ける。
6. **1件以上のアイデアが残れば、元の2枚は使用済みとし、同じゲーム中に再登場させない。全員空なら、2枚を裏へ戻して再利用可能にする。**
7. 未使用カードが2枚以上あれば、直前の手番ユーザー以外から次の担当をランダムに選ぶ。2枚未満ならゲームを終了し、次の担当は選ばない。

各手番は「1人が2枚を選ぶ段階」と「全員が書く段階」で構成する。配布・抽選対象は、その手番の入力開始時点に接続しているユーザー。途中参加したユーザーは次の手番から参加する。切断時の担当交代などは別途定める。

| 項目 | 既存実装で確認できたこと |
| --- | --- |
| ボード | `Board` は `boardId`・`cards`・`arrows`・`timer` を持つ。作業フェーズはまだない |
| カード | `WordCard`（`cardKind: 'word'`）と `BlockCard`（`cardKind: 'block'`）。本文はいずれも `text` |
| ID | `CardId` は文字列ではなく `{ type: 'card', uuid: string }`。比較は `sameObjectId`、ReactやMapのキーには `objectKey` を使う |
| クライアント | `BoardClientState` は、確定済みの `board` と端末固有の編集・送信状態などを保持する |
| 操作の送信 | `POST /api/boards/:boardId` へコマンドを送る |
| 初期取得と同期 | `GET /api/boards/:boardId/events?userId=...&clientId=...` のSSEで初期スナップショットと以降の更新を受信する |
| サーバーからのデータ | `BoardEvent` に `board`・`revision`・`serverNow`・`generation`・`generationSequence` を含める。`BoardClientState` 自体を配信する仕組みではない |
| 共有タイマー | 初期5分。0秒で停止し、`onTimerFinished` を呼ぶ。現在の終了フックは空で、フェーズは変わらない |
| 単語生成 | 手動要求と、カード系更新後30秒の待機による自動追加がある。実際に接続されている生成関数はモックで、アイデア生成・組み合わせ判定はない |
| 保存先 | 単一プロセスのメモリ。ボードやタイマーは再起動で失われる |

参照：[共通モデル](../src/domain/board.ts)、[通信の型](../src/domain/board-protocol.ts)、[クライアント](../src/client/board-client.ts)、[サーバー](../src/server/board-service.ts)、[現在の実装状況](./implementation.md)。過去の計画書に記載があっても、現行コードにない機能は実装済みとして扱わない。

なお、既存の `state.edit.phase` は `idle`・`requesting`・`editing` などの**編集手続きの状態**であり、単語出し・神経衰弱といった作業フェーズには流用しない。

## 2. 必要なデータと、その持ち主

### 2.1 作業フェーズと手番の共有状態（追加案）

共有モデルの `Board` に `phase` を追加する。通常の編集ボードを `word`、神経衰弱を `matching` とする案とし、ゲーム終了時は `word` へ戻す。神経衰弱の中でカード選択とアイデア入力を繰り返すため、その段階は `matching.turn.step` などで区別する。元案の `idea`・`evaluation` を独立したフェーズとして追加する仕様は採用していない。

| データ候補 | 用途 |
| --- | --- |
| `sessionId` | 1ゲームを識別し、前のゲームの遅延した操作を拒否する |
| ゲームの状態 | `active` / `finished` などで実行中と終了済みを区別する。終了済みのゲームは次の担当・入力期限を持たず、そのゲームへの変更操作を拒否する。通常のボード編集は再開する |
| 接続中の `userId` 一覧 | カードの配布先と手番候補を管理する。同じユーザーの複数タブを別の参加者として数えず、1つでも接続があれば接続中とする案とする |
| `turnId`・`selectorUserId` | 現在の手番と、2枚を指定できるユーザーを識別する |
| 手番の段階 | `selecting`（担当が2枚を指定）と `writing`（全員が入力）を区別する |
| 対象カードID・表示順 | 開始時点で本文のある `WordCard` を対象にし、サーバーで一度シャッフルした順序を共有する |
| 選択中のカードID | 0〜2枚。2枚は異なるIDで、今回のゲームの選択対象に含まれる未使用カードに限る |
| 今回の入力対象ユーザー | 入力開始時点の接続ユーザーで固定する。入力中の新規参加者には、その手番のカードを後から配らない |
| ユーザーごとの下書き一覧 | `Board.matching.drafts` などで、入力者・入力用カード・本文・入力順を全員に共有する。`Board.cards` の公開済みカードとは別に保持する |
| `endsAt` | 2枚目と全員分の下書きの作成を確定したサーバー時刻＋10,000ms |
| 各手番の結果 | 選ばれた2枚、追加した `blockCardId` と書いた `userId` の対応などを保存する |
| 使用済みのカードID | 1件以上の本文が追加された手番の2枚を、以降の選択対象から除外する。結果から導出するか、整合性を検証して保持する |

例えば `Board.matching` にゲームの進行状態と全員分の下書きを追加する。毎秒の残り秒数は配信せず、各端末が同じ `endsAt` から計算する。続行時の担当者はサーバーで一度だけ抽選し、決まったユーザーを共有する。終了状態では現在の手番・期限処理を終了し、通常の編集モードに戻して、公開したカードとユーザー対応を残す。

**使用済みの単語カードは `Board.cards` から削除しない。** 神経衰弱の選択対象から外すことで、追加した `BlockCard.relatedIds` が元の2枚を参照し続けられる。全員空の場合は2枚を裏へ戻し、使用済みにしない。

**シャッフルはゲーム専用の表示配置として管理し、元の `Board.cards` の `position` を変更しない設計とする。** サーバーがゲーム開始時に一度決めた順序から全員が同じ配置を表示する。全員空でカードを戻す場合も、この順序を保つ。

終了時は専用の配置・表裏表示を解除するため、元の座標でカードを表示できる。ゲーム開始前の `Board` 全体を保存して上書き復元する方式にはしない。これにより、ゲーム中に追加したアイデアやユーザー対応を消さずに元の配置へ戻せる。

### 2.2 ユーザーごとの入力用カード・下書き（追加案）

**入力中のカードは、盤面に追加済みの `Board.cards` と分けて管理する。** `Board.matching.drafts` などを使って入力途中から本文を全員に公開し、10秒後に本文のあるものを `Board.cards` へ移す。「全員が読めること」と「通常のボードカードとして追加済みであること」を区別する。

| データ候補 | 用途 |
| --- | --- |
| `sessionId`・`turnId`・`ownerUserId` | 誰の、どの手番の下書きかを識別する。1ユーザーにつき1枚 |
| 入力用の `BlockCard` | 一意の `cardId`、空の初期本文、その手番の2枚を指す `relatedIds` を持つ。盤面への追加後も同じIDを使う案とする |
| 入力元の `clientId`・入力連番 | 同じユーザーの複数タブや、前後して届く入力による本文の巻き戻しを防ぐ |
| サーバーが受理した最新本文 | 10秒後に残す内容。カードの本文上限など既存の検証に従う |

サーバーが共有の下書き一覧を保持し、全クライアントが全員分を閲覧できる。各参加者が編集できるのは自分に配られたカードだけとし、ほかのユーザーのカードへの書き込みは拒否する。`selectorUserId` は単語を選ぶ担当であり、入力できる人を1人に制限する属性には使わない。端末には自分の未送信入力や保存状況を表示するためのローカル状態を持つ。

現行クライアントは画面を開き直すと `clientId` が変わるため、入力権を古い `clientId` に固定したまま再接続を許可すると不整合になる。再接続時は本人の受理済み下書きを取得し、新しい入力元へ引き継ぐ方式を設計する。入力元の世代やサーバー側の下書きバージョンを使い、旧接続の遅い更新も拒否する。単なる端末ごとの連番だけで順序を保証できるとは扱わない。

入力用カードの作成は、空の `BlockCard` と2枚への関連付けをサーバーで作る処理。AIによる本文生成はこのルールに含めない。現在の `card.create` は空の関連先しか受理しないため、専用の作成経路が必要になる。

入力中の本文は受理した更新から全員へ配信する。閲覧は共有、書き込みは所有者だけというルールを、UIとサーバーの両方で適用する。新規参加者も現在の全員分の下書きを閲覧できるが、自分のカードが配られるのは次の手番から。

### 2.3 カードと書いたユーザーとの対応

盤面へ追加する各カードには、手番の担当者ではなく、**そのカードを書いたユーザー**を対応付ける。`blockCardId`・`ownerUserId`・`sessionId`・`turnId` などを結果レコードやカードのメタデータとして保持する案とする。保存先は、ゲーム終了後も対応を失わないように決める。

既存の `editingUser` は編集貸し出しの一時状態で、解除時に消えるため、この対応には使わない。空の下書きを破棄した際は、存在しないカードへの結果参照を残さない。

### 2.4 画面用の状態

`MatchingCardItem[]` を作る場合も、共有状態と元カードから表示用に導出する。受信したカードを別の正本としてコピーし続けない。

- `isFlipped`：共有の選択状態から計算する。
- `isUsed`：今回のゲームで使用済みになったかを表す。
- アニメーション中・ホバー・入力のローカル表示・送信待ち・表示範囲：端末固有のUI状態として保持する。

今回のルールには同じ内容のペアを探す判定はないため、元案の `isMatched` は使わない。既存モデルと `BoardClientState` は読み取り専用として扱い、画面から直接変更しない。

## 3. データを受け渡すタイミング

### 3.1 単語出しからゲームを開始するとき

1. 誰でも開始ボタンからゲーム開始コマンドを送信できる。サーバーで一度だけ開始を確定する。
2. サーバーが現在のフェーズ、編集ロック、選択対象、参加者、進行中の単語生成を確認する。
3. 開始時点の本文のある単語カードから対象を決め、サーバーで表示順を一度シャッフルする。`sessionId` と最初の `turnId` を作り、開始要求を受理したユーザーを担当にする。
4. フェーズと進行状態をまとめて確定し、既存のSSEで全員へ配信する。対象の単語カードを裏向き・ゲーム専用の配置で表示し、元のボード座標は変更しない。

開始時には対象の単語が2枚以上、接続ユーザーが2人以上いることを検証する案とする。同時に開始ボタンが押された場合は最初に受理した要求だけでゲームを開始し、そのユーザーを最初の担当とする。

編集中の下書きは既存ボードの確定状態に含まれない。編集ロックがある場合に開始を拒否するか、編集終了を待つかは要確認。無条件で下書きを破棄する仕様にはしない。

### 3.2 手番の担当が2枚を指定するとき

画面から `client.execute(...)` を通して `sessionId`・`turnId`・`cardId: CardId` を送る案とする。サーバーは手番の本人、選択段階、カードの存在・対象範囲・使用済みでないことを確認する。

1枚目なら共有の選択状態を更新する。2枚目なら、次を一括して確定する。

1. 異なる2枚を選択済みにする。
2. 今回の入力対象ユーザーを確定し、**手番の担当を含む全員分**の入力用 `BlockCard` を1枚ずつ作る。各カードの `relatedIds` は同じ2枚とする。
3. 段階を `writing` にし、全員共通の `endsAt = サーバー時刻 + 10,000ms` を記録する。
4. 期限処理を予約し、全員に進行状態と全員分の入力用カードを配信する。各ユーザーは自分のカードを編集でき、他人のカードは閲覧できる。この時点では `Board.cards` に追加しない。

入力中は3枚目を指定できない。同じ操作の再送で入力用カードを増やしたり、10秒を計測し直したりしない。各端末の受信時刻から個別に10秒を数える方式にはしない。

### 3.3 全員が同時に書き込むとき

各参加者は自分の下書きへ入力する。途中まででも残し、入力中から全員へ見せるため、画面内だけに本文を保持せず、下書き保存要求でサーバーへ随時送る。受理した本文の更新を全員へ配信する。

サーバーは `sessionId`・`turnId`、入力段階、期限、自分に配られたカードであること、入力順序を検証する。単語選択の担当でなくても、自分のカードには書ける。入力元と連番により、古い本文の遅延到着で最新本文を上書きしない。

下書きの保存では期限を延長せず、盤面への追加・使用済み化・次の担当の抽選も行わない。全員が早く書き終えても、確認済みのルールでは共通の時間終了時に処理する。

### 3.4 10秒後の終了処理

サーバーは、期限までに受理した各ユーザーの最新本文を基準に、次を一括して確定する。

1. 対象の `sessionId`・`turnId` と入力段階を確認し、この手番の入力受付を終了する。
2. 本文のある下書きを抽出する。空判定は `text.trim()` が空かで行う案とする。
3. 本文のある全 `BlockCard` を `Board.cards` へまとめて追加し、それぞれを入力者へ関連付ける。途中の本文も対象にし、空の下書きは破棄する。
4. 1枚以上追加した場合は元の2枚を使用済みにする。0枚なら2枚を裏向きへ戻す。
5. 未使用カードが2枚未満ならゲームを終了し、専用の表裏・シャッフル表示を解除して通常の編集ボードへ戻す。次の手番は作らない。2枚以上なら、**直前の担当者以外**の候補から次の担当をランダムに1人選ぶ。新しい `turnId` と選択状態を作る。
6. 使用済み状態、追加カード、結果、終了状態または次の担当を含む最新のボードを配信し、終了した手番の下書き領域を片付ける。

| 入力結果 | 盤面へ追加するもの | 元の2枚 | 未使用カードが2枚以上ある場合の次の担当 |
| --- | --- | --- | --- |
| 全員が入力 | 全員分の本文入り `BlockCard` | 使用済み | 直前の担当以外からランダム |
| 一部のユーザーだけ入力 | 入力のあるユーザー分だけ | 使用済み | 直前の担当以外からランダム |
| 全員空 | 追加なし | 裏へ戻して再利用可能 | 直前の担当以外からランダム |

入力の有無にかかわらず、抽選から外すのは直前に2枚を指定した担当者。未使用カードが2枚未満なら、表の入力結果によらずゲームを終了する。入力開始後に切断したユーザーを抽選時にも候補に含めるか、次の候補がいない場合にどうするかは要確認。

終了後に届いた下書き保存で、追加済みカードや次の手番を上書きしない。保存対象は期限までにサーバーが受理した本文とし、未送信・通信中の入力が必ず残るとは扱わない。

## 4. クライアントとサーバーの通信（追加案）

既存のHTTP POSTとSSEを拡張する。新しいWebSocket接続や別サーバーは不要。

### 4.1 クライアントからサーバーへ

以下のコマンド名・属性は**追加案であり、現状のAPIには存在しない**。

| コマンド案 | 追加属性 | 意味 |
| --- | --- | --- |
| `matching.start` | 追加属性は設計時に決定 | 誰でも開始ボタンから要求できる。開始条件をサーバーで検証し、受理したユーザーを最初の担当にする |
| `matching.reveal` | `sessionId`・`turnId`・`cardId: CardId` | 手番担当が1枚指定。2枚目で全員分の下書きと共通期限を作る |
| `matching.update-draft` | `sessionId`・`turnId`・`blockCardId`・`text`・入力連番 | 各参加者が自分の下書きを保存する |

すべての要求に既存と同じ `boardId`・`userId`・`clientId`・`requestId` が必要。`client.execute` を使う画面は操作部分だけを渡し、クライアントが識別情報と要求IDを付ける。

例：担当者が1枚を指定するHTTP本文の案。

```json
{
  "type": "matching.reveal",
  "boardId": "demo",
  "userId": "user-1",
  "clientId": "tab-1",
  "requestId": "request-1",
  "sessionId": "matching-session-1",
  "turnId": "turn-1",
  "cardId": {
    "type": "card",
    "uuid": "00000000-0000-4000-8000-000000000001"
  }
}
```

IDは実際に配信されたものを使う。入力者は要求の識別情報から決め、他人のユーザーを任意指定して保存・関連付けできないようにする。本文保存ごとに新しい要求IDを発行し、同じ本文保存の再送には元の要求IDを使う。

入力時間の終了と盤面への追加、ゲームの終了判定、続行時の担当者の抽選はサーバーが行う。各ユーザーの手動確定で手番を終了させる操作は設けない。未使用カードが2枚未満になった場合の終了に専用のクライアント要求は不要。途中でゲームを中断する操作の有無は要確認。

### 4.2 サーバーからクライアントへ

- 既存の `command.accepted` / `command.rejected` で要求結果を返す。
- `Board.matching` に全員分の下書きを含め、既存の `board.snapshot` などで全員へ配信する。受理した本文更新も共有ボードの変更として `revision` を進める案とする。期限終了で複数枚を追加する処理は、途中状態を出さず一括更新する。
- 入力要求の順序はユーザーごとの入力元の世代・連番や下書きバージョンで検証する。受信したボード全体の順序は既存の `revision` で扱い、古いスナップショットで他人の本文も巻き戻さない。
- `BoardClientState.board` から全員の入力用カードを取得し、自分の未送信入力と保存状況はローカル状態で扱う。通常のカード編集を表す `edit` と分ける。
- 初期取得・再接続で、現在の担当、選ばれた2枚、共通期限、シャッフル順、全員分の下書き、ゲームの終了状態を復元する。配布対象だったユーザーだけが本人の下書きへの入力を再開できる。再接続で期限を延長しない。
- 入力開始後に初めて参加したユーザーは、その手番を見学する。配布済みの本人分の下書きがある前提で復元したり、新しい入力カードを追加したりしない。
- 古いボード応答で公開状態を巻き戻さない。下書き更新の返答や再送で、終了済みの入力画面を復活させない。

本文は全員に公開するため、本人専用の下書きスナップショットを作る方式は不要。`Board.matching.drafts` の共通モデル・受信検証・初期化を拡張する。全員に同じ下書きが届いても、書き込み時の所有者検証は必要。

## 5. 既存機能との整合性

### 通常の編集・カード生成

ゲーム用下書きは `Board.cards` の外にあるため、通常の `edit.request` / `edit.commit` では編集しない。専用の入力・保存経路で本人の下書きを変更し、本文は全員へ配信する。入力終了時にまとめて通常のボードカードへ変換する。

元の単語や関連先を、ゲーム中に通常の編集・削除で壊せないようにする案とする。移動・追加・全消去・サンプル復元・JSON読み込み、公開されたアイデアの後編集などの可否は要確認。制限する場合はUIとサーバーの両方で検証する。

現在の `board.import` はカードIDを新しく割り当てて盤面全体を置き換える。ゲーム用下書きは通常の編集ロックを持たないため、既存の「編集中なら読み込み拒否」だけでは進行中のゲームを保護できない。ゲーム中は読み込みを拒否するか、ゲーム終了と下書き・期限処理の無効化まで一括して行う必要がある。

既存のカードUIは本文へのフォーカスで編集を開始するため、神経衰弱の単語選択UI・個別入力UIを通常編集と競合させない。

### 単語の自動生成

現在の `onBoardUpdated` にはカード系更新後に自動単語追加の待機を設定する経路があり、JSON読み込みは待機を作らない例外として扱われている。ゲームの進行、下書き保存、期限後の複数カード追加も、意図せず単語生成を起動しないよう更新種別と条件を整理する。

単語出し中だけ生成する案とし、待機設定・満了・手動要求・生成結果の適用時にフェーズを確認する。ゲーム開始時に待機を取り消し、すでに走っている古い生成結果も無効化する。今回の入力用 `BlockCard` 作成に `generation.request` は使わない。

ゲーム終了で通常編集のフェーズへ戻す更新も、ゲーム進行による更新として自動生成の待機を作らない。終了直後にアイデア本文を材料として単語追加が始まらないようにし、以後の通常編集による更新から既存の待機を適用する案とする。

### 共通の10秒と終了処理

回答期限は `matching.turn.endsAt` とサーバー側の予約処理で管理する案とする。既存の `Board.timer` は初期5分で、誰でも開始・停止・リセットできるため、そのまま回答期限には使わない。表示には既存の `serverNow`・`serverOffsetMs` を利用できる。

`now >= endsAt` なら下書き更新を受け付けない案とし、予約コールバックがまだ動いていなくても期限は延長しない。終了処理は `sessionId`・`turnId`・入力段階を確認し、一度だけ実行する。本文抽出・複数カード追加・使用済み化・結果保存・次の担当者の抽選を、途中に `await` を挟まず一括して確定する。

予約コールバックの重複、要求の再送、古い手番のイベントによってカードを二重追加したり、次の担当者を抽選し直したりしない。ランダムな結果は確定後に配信し、端末ごとには抽選しない。

ゲーム開始は手動なので、既存の共有タイマー終了フックから神経衰弱へ移行する処理は追加しない。開始ボタンを押した時点で共有タイマーが動作中だった場合に停止するかは別途決める。共有タイマーの終了を、10秒の回答期限と混同しない。

### 参加者・次の担当者

現在のボードには参加者登録や手番担当の管理がない。`userId` 単位で参加者を管理する仕組みを追加し、配布対象と抽選候補を確定する必要がある。

各手番の入力開始時点で接続しているユーザーを、配布・抽選対象の基準にする。次の担当者の抽選では直前の担当者を除外する。2人が接続し続ける場合は担当が交互になる。3人以上では同じ人が全員一巡前に再び選ばれることもある。

途中参加は次の手番からとし、現在の手番の配布対象に後から追加しない。既に配布されたユーザーが切断しても、その時点までに受理した下書きを即座に消す処理は行わず、10秒後の本文抽出の対象として保持する案とする。

最初の担当は開始ボタンの要求を受理したユーザーとする。開始条件は接続中のユーザー2人以上とする案。開始後に1人になった場合、入力開始後に切断した人の抽選資格、次の候補がいない場合、選択担当が2枚を選ばず止まった場合は要確認。10秒は2枚指定後なので、選択中の停滞には別の扱いが必要になる。

現在の `userId` / `clientId` は識別情報で、認証ではない。開始は誰でも要求できるため、この機能の開始操作のために代表者権限は追加しない。

### 保存とユーザー対応

現在のJSON書き出しは公開カードと矢印を保存するため、盤面に追加済みの `BlockCard.text`・`relatedIds` は対象になる。盤面へ追加する前のゲーム用下書きや、別領域に置いたユーザー対応・手番結果は、そのままでは保存されない。

ユーザー対応の保存先、JSONへの出力範囲、ゲーム途中の再開を必要とするかは別途決める。現状のメモリ実装では、サーバー再起動でゲーム状態・下書きも失われる。

### ゲーム終了と元の盤面表示への復帰

未使用カードが2枚未満になったら、最後の本文入りカードを追加したうえで通常編集へ戻す。元からある単語・既存の `BlockCard` と、新しく追加したアイデアをすべて残す。

元のカードのボード座標を維持し、ゲーム中だけ別の表示配置を使う。終了時はその表示を解除して、使用済みだった単語も含めて通常の表向き表示に戻す。ゲーム中に追加するアイデアの通常座標もサーバーが決め、元カードの復帰位置と重ならない配置にする案とする。

終了済みゲームへの遅い要求・期限処理は拒否または無視し、通常の編集を上書きしない。もう一度開始する場合は新しい `sessionId` と未使用状態でゲームを作り、前のゲームで生成したアイデアとユーザー対応は残す設計案とする。

## 8. 実装後に確認する動作

- 最初に受理した開始要求のユーザーが最初の担当となり、全員に同じシャッフル順・裏向き表示が配信される。
- 選択担当だけが2枚を指定でき、異なる有効な2枚を確定したら全員に1枚ずつ入力用カードが配られる。
- 担当者以外も自分のカードへ入力でき、ほかのユーザーの下書きへの保存は拒否される。
- 下書きは入力中に `Board.cards` へ混入せず、10秒の開始時刻と終了期限は全員で一致する。
- 下書きの本文は入力途中から全員に共有され、他人のカードは閲覧だけできる。古いスナップショットで本文が巻き戻らない。
- 全員入力・一部だけ入力・全員空の各場合に、残すカード枚数と使用済み判定が正しい。
- 終了時に追加されるカードは正しい元2枚を参照し、各カードを実際に書いたユーザーと対応付けられる。
- 下書き保存の前後逆転、同じ要求の再送、古い手番の遅延操作で本文が巻き戻ったりカードが増えたりしない。
- 期限処理が二重に呼ばれてもカード追加は一度だけ。未使用カードが2枚以上ある場合だけ次の担当を抽選し、直前の担当を除外して全員へ同じ結果を配信する。
- 未使用カードが2枚未満になったら、最後のアイデアを残して元のカード配置・表向き表示・通常編集へ戻る。新しい手番や入力期限を作らない。
- 期限後の入力、再接続、共有タイマー操作で10秒が延長されず、次の手番に古い処理が影響しない。
- 再接続・途中参加でも全員分の下書き本文を閲覧できる。配布対象だったユーザーは自分の入力を再開できる。入力開始後の新規参加者は見学し、自分の入力カードを持たない。
- ゲーム終了時に開始前のボード全体を上書きせず、新しく追加したアイデア・ユーザー対応と元のカードを維持する。
- クライアントを開き直して入力元の `clientId` が変わっても、合意した再接続の仕様に従って下書きを引き継ぎ、旧入力元の遅い更新で巻き戻らない。
- ゲームの操作で意図しない単語生成を起動せず、既存の編集・リアクション・矢印・共有タイマー・再送に回帰不具合がない。
